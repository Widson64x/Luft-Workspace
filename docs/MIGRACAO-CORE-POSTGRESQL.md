# Migração do núcleo sistêmico para PostgreSQL

[Voltar à documentação do Luft-Workspace](README.md)

## Objetivo

O utilitário `scripts/migrar_core_postgresql.py` cria o schema `core` no banco
`luft_web` e copia as 13 tabelas sistêmicas atualmente distribuídas entre os
SQL Servers de produção e homologação.

O SQL Server é tratado estritamente como origem somente leitura. A aplicação
instala uma barreira no SQLAlchemy que aceita apenas comandos iniciados por
`SELECT` ou `WITH`. Toda criação, carga, criação de chaves e criação de índices
acontece exclusivamente no PostgreSQL.

## Bancos utilizados

| Papel | Caminho no Vault | Acesso do migrador |
|---|---|---|
| Origem PRD | `luft/producao/sqlserver` | somente leitura |
| Origem HML | `luft/homologacao/sqlserver` | somente leitura |
| Destino | `luft/desenvolvimento/postgresql` | leitura e escrita |

O destino é recusado caso `current_database()` não retorne `luft_web`. Nenhuma
URI ou credencial é exibida.

## Origem dos dados

Produção fornece:

- `Tb_Sistema`;
- `Tb_Permissao`;
- `Tb_PermissaoGrupo`;
- `Tb_PermissaoUsuario`;
- `Tb_LogAcesso`;
- `Tb_LogDetalhe`;
- `Tb_Notificacao`;
- `Tb_Notificacao_Leitura`.

Homologação fornece:

- `Tb_Publicacao`;
- `Tb_PublicacaoGrupo`;
- `Tb_PublicacaoLeitura`;
- `Tb_PublicacaoNotificacao`;
- `Tb_NotaAtualizacaoItem`.

`Tb_PublicacaoNotificacao` referencia notificações de homologação. Por isso o
migrador também copia apenas as linhas de `Tb_Notificacao` de HML vinculadas a
uma publicação. Se algum ID já existir entre as notificações de PRD, o ID de
HML é remapeado e o vínculo recebe o novo valor.

Os IDs de sistema de HML são relacionados a PRD pelo nome do sistema. A carga é
cancelada se uma publicação usar um sistema que não tenha equivalente em PRD.

## Estrutura de destino

Os nomes do PostgreSQL são minúsculos e permanecem próximos dos nomes legados,
por exemplo `core.tb_logacesso` e `core.tb_publicacaonotificacao`.

Campos `varchar(max)`, `nvarchar(max)` e `text` do SQL Server são criados como
`text`. Isso evita o truncamento produzido pelo mapeamento automático do
DBeaver. Chaves numéricas geradas utilizam `GENERATED BY DEFAULT AS IDENTITY`,
permitindo copiar os IDs históricos e continuar a numeração depois da carga.

As chaves estrangeiras são criadas apenas entre tabelas presentes no
PostgreSQL. Códigos de usuário e grupo continuam apontando logicamente para
`Luftinforma`; eles recebem comentários no catálogo, mas não uma chave física
impossível de validar entre bancos diferentes.

A estrutura acrescenta índices para:

- pesquisas de permissão por sistema, grupo e usuário;
- auditoria por data, sistema, usuário e recurso;
- notificações por usuário, grupo, sistema, leitura e expiração;
- publicações por escopo, status, origem externa, grupo e leitura.

## Execução segura

No diretório do Luft-Workspace, execute primeiro o diagnóstico:

```powershell
.\.venv\Scripts\python.exe scripts\migrar_core_postgresql.py
```

Esse comando consulta as origens, valida tabelas e vínculos, mostra contagens e
consulta o destino. Ele não grava em nenhum banco.

Depois de revisar o plano, execute a migração:

```powershell
.\.venv\Scripts\python.exe scripts\migrar_core_postgresql.py `
  --executar `
  --confirmar MIGRAR_CORE_LOCAL
```

A criação das tabelas, a carga, as chaves, os índices, o ajuste das sequências e
as validações de contagem ficam na mesma transação PostgreSQL. Qualquer erro
provoca rollback integral.

Como as aplicações continuam registrando auditoria em produção, o migrador
captura os maiores `Id_Log` e `Id_LogDetalhe` no início da carga. Somente IDs até
esses limites entram na execução. Isso evita bloquear a origem e impede que um
detalhe criado durante a cópia seja levado sem o respectivo log de acesso.

## Destino já preenchido

Por padrão, o migrador recusa qualquer uma das 13 tabelas já existente. Para
uma substituição consciente:

```powershell
.\.venv\Scripts\python.exe scripts\migrar_core_postgresql.py `
  --executar `
  --confirmar MIGRAR_CORE_LOCAL `
  --substituir `
  --confirmar-substituicao SUBSTITUIR_TABELAS_CORE
```

Antes de remover as tabelas gerenciadas, o migrador copia seus dados para um
schema como `core_backup_20260915_153000`. A remoção não usa `CASCADE`; uma
dependência externa inesperada faz a operação falhar e a transação restaura o
estado anterior.

## Validação posterior

Após a conclusão, verifique:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'core'
ORDER BY table_name;
```

O resultado deve conter 13 tabelas. Também valide o login e as permissões nas
aplicações somente depois que os modelos forem alterados para consultar o
PostgreSQL. A migração não altera automaticamente os projetos consumidores.
